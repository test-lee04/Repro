# 반복 평가 진행 순서

현재 결과 보고서와 JSON 사본을 먼저 저장한다. 이번 묶음은 docs/evaluation 안의 문서만 포함하며 앱 코드나 프로젝트 루트 README를 교체하지 않는다.

## 1. 보고서 보존

프로젝트 루트에 이 묶음의 docs 폴더를 병합한 뒤 실행한다.

```bash
git add -- docs/evaluation
git diff --cached --stat
git commit -m "docs: 자동 평가와 확인 답변 후 평가 결과 기록"
git push origin main
```

원본 artifacts 폴더와 가상환경은 추가하지 않는다. 문서 커밋은 앱 코드 내용 식별값을 바꾸지 않는다.

## 2. 자동 평가를 자료별 두 번 추가 실행

```bash
python -m eval.run_eval --case all --repeats 2 --verify-tests
```

새 폴더에서 총 14건을 실행한다. 기존 7건 결과를 덮어쓰지 않는다. 현재 자료에서 관찰한 시간으로는 약 16분 안팎의 실행이 예상되지만 모델 응답 시간에 따라 달라질 수 있다. 실패와 보류도 그대로 남긴다.

우선 이 명령의 전체 로그와 새 보고서 경로를 공유한다. 사례별 결과가 반복되는지, 새 오류나 시간 초과가 생기는지 확인한다. 이 단계에서는 코드나 모델을 바꾸지 않는다. 기존 1회 결과와 새 반복 결과의 앱 코드 및 자료 식별값도 대조한다.

## 3. 자동 평가 결과 확인 후 답변 후 평가를 별도 실행

```bash
python -m eval.run_eval --case validation --confirmed-plan artifacts/verification-plan-a2fbdfc27b3140faac2ca21b59dec772 --repeats 2 --verify-tests
```

두 환경을 각각 두 번, 총 4건 실행한다. 이전 답변 기록을 그대로 사용한다. 이전 실측으로는 수 분이 필요하며 실제 시간은 달라질 수 있다. 자동 평가의 14건과 성공률을 합치지 않는다. 답변 이전 시간은 이 실행에 포함되지 않는다.

## 비교할 항목

- 각 자료와 환경에서 판정이 반복해서 같은지.
- 정답과 일치한 횟수 및 질문 또는 오류로 끝난 횟수.
- 정상 환경의 오탐과 정상 환경에서 판정을 보류한 횟수.
- 테스트 생성 여부, 같은 테스트의 원래 환경 실패와 정상 환경 통과.
- 실제 모델 호출 수와 실행 시간의 차이.

동일한 잘못된 결과가 반복된 것은 일관성은 있지만 정확한 것은 아니다. 두 번의 추가 실행만으로 모든 상황의 안정성을 입증할 수도 없다. 반복 결과를 본 뒤 개선 우선순위와 발표에 사용할 수치를 정리한다.
